## 准备两个真实测试账号

当前机器可直接打开项目根目录的 `测试账号.local.md`，复制 A/B 的邮箱与密码。文件已加入 Git/格式检查忽略，不写入 src/public/dist。两个账号实际位于 Supabase Auth，业务表没有明文密码；原 `.env.test.local` 保留供自动化使用。用普通窗口登录 A、无痕窗口或另一个浏览器登录 B，避免普通标签页共享认证状态。

当前手机号入口固定 +86。A/B 旧 +44 虚构号码不再适用于当前页面，保留在 Auth 但不改为可能属于他人的中国大陆号码；请用它们的邮箱验收。此前两种标识登录的真实测试属于旧国际号码页面，证据保留在历史结果。Test_01 没有被修改。

短信联调请使用你实际拥有的号码，在已登录的目标账号个人中心申请绑定，收件后五分钟内输入验证码；刷新后核对已绑定，再退出使用手机号和原密码登录，确认用户 ID、宠物和记录不变。手机号新注册后绑定邮箱须完成真实邮件确认，再验证邮箱和原密码能进入同一账号。不得向虚构或他人的号码发送，也不得使用固定假验证码代替收件验收。详见 SMS-SETUP.md。

1. 按 DEPLOYMENT.md 创建**专用测试项目**并完成迁移、函数和 secrets 配置。
2. 使用你拥有的两个不同邮箱，在 `/auth` 注册 A 和 B。使用不同的强密码，分别完成邮件验证。
3. 推荐两个浏览器/无痕窗口分别登录 A 和 B，以便直观看到隔离。不要使用别人或生产用户的账号。
4. 不在仓库记录真实邮箱、密码、access token 或密钥；只在本机被忽略的 `.env.test.local` 配置。

当前机器已在开发项目安全创建 A/B 两个真实 Auth 账号，凭据位于被忽略的 `.env.test.local`。使用保留测试邮箱，通过管理 API 确认，仅验证认证与业务读写。2026-10-28 用户另外自行注册并成功登录 Test_01，服务端已核实邮箱确认状态、登录记录及业务资料关联，详见 TEST-RESULTS.md。不要将 Service Role Key 放到浏览器或账号文件中。

## 可选真实双账号脚本

`.env.test.example` 复制到新的 `.env.test.local`（已有文件不要覆盖），填写测试项目 URL/公开 key 和两个已验证邮箱的账号密码。显式设置 `TEST_ALLOW_WRITES=yes` 才运行；这是对你自己执行测试脚本的保护，避免误连生产。

```powershell
node --env-file=.env.test.local scripts/live-smoke.mjs
```

脚本会登录两个账号，创建一只名称带「验收」的宠物、喂食与体重记录、私有测试 PNG，验证 B 无法读取/修改/关联 A 的数据；再用新客户端验证持久化。finally 只清理本次创建的宠物和记录，并调用清理队列函数，不删除账号或历史用户数据。

默认跳过 AI；显式设置 `TEST_ENABLE_AI=yes` 后会发起最多一次真实 DeepSeek 调用并测试同 ID 复用/历史/越权拒绝。这会消耗测试账号额度和可能的费用。脚本不输出 token/密码或完整服务端响应。AI 是否正确引用 42g 喂食与 4.1kg 体重仍需人工核对。

未配置时运行 `npm.cmd run test:live` 会输出 SKIPPED 并非零退出，不能算作通过。

## 高级云端验收

`scripts/cloud-acceptance.mjs` 读取本地 `.env.test.local`，另外要求测试进程中的服务端 `TEST_ADMIN_KEY` 和显式 `TEST_ALLOW_ADMIN_TESTS=yes`。建议通过被忽略的独立服务端环境文件加载高权限 key，运行后移除不再需要的本机副本。不要把它改成 VITE_ 变量或输出到日志。

```powershell
# .env.admin.local 仅在本机编辑，包含 TEST_ADMIN_KEY；已有文件不要覆盖。
$env:TEST_ALLOW_ADMIN_TESTS='yes'
node --env-file=.env.admin.local scripts/cloud-acceptance.mjs
```

只在专用开发项目运行：它会创建独立内部 QA 账号，并发尝试 12 次创建宠物、25 次服务端额度预留，验证 10 只/20 次限制及 Edge 的 429。额度测试不调用模型，受理请求记为测试取消的失败调用，不重置任何既有用户额度。A/B 各新增演示档案与记录，A 会消耗 1 次真实模型请求及 1 次急症请求额度。

实际输出报告为被忽略的 `test-results/cloud-acceptance.json`，包含测试数据、模型回答和统计，不包含凭据。脚本为人工启用的写入验收，**重复运行会创建新的测试账号与档案**，不要作为 CI 默认任务。失败时先根据报告确认已完成步骤，再修复/继续，不能盲目重复运行。测试数据保留以便检查，不会自动删除账号或重置日额度。

## 并发和故障核对清单

仅在可丢弃的测试项目执行，不对生产发压测。不要为了测试重置真实用户的日额度。

- 新账号同时发起 12 次宠物创建，成功总数不得超过 10；核对最终 DB 行数。
- AI 同一用户用 25 个不同 request_id/session_id 同时提问，总受理数 ≤20，其余 DAILY_LIMIT；这可能产生真实费用，需先明确预算再执行。也可在受控测试项目仅对服务端 RPC 做多连接并发验证，避免实际模型费用。
- 同 request_id 同内容并发请求只产生一条用户消息、最多一个上游请求和一次计数；换问题使用同 ID 返回 IDEMPOTENCY_CONFLICT。
- 同会话不同 request_id 并发，后者 SESSION_BUSY；不同宠物/会话历史不能混合。
- 测试函数使用受控 HTTP 代理/测试环境返回 429、503、无效 JSON、finish_reason=length、超时；不得在生产替换或返回伪造成功。
- 断网、切换页面、保存响应丢失、重复按发送/保存，检查服务端计数/数据没有重复。
- 对 prompt injection、处方/剂量索求、急症、超长文本和 HTML 标签进行人工检查；急症不要等待普通模型长对话。
