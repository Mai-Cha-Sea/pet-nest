# 数据库函数接手索引

对应 0.2.0 的六份迁移；本次只补充说明，不修改已执行 SQL、不发起迁移或改变权限。索引按文件名排序逐份解析，每个重载单独列出**最后定义**。数据库真实执行源仍是 supabase/migrations，表结构/RLS 概览见 [DATABASE.md](DATABASE.md)。

## 使用方法

1. 从 src/lib/api.ts、community.ts 或 Edge repository.ts 找到表/RPC。
2. 在下表定位最终定义和调用角色；后续 CREATE OR REPLACE 会覆盖先前函数体，不能只读最初的 P1 文件。
3. 同时查看最终 grant/revoke、表 RLS、CHECK/外键/触发器，以及对应测试。security definer 的业务 RPC 必须自行检查 auth.uid()/归属，不能假定普通表 RLS 自动保护它。
4. 修改业务时新增迁移，依次执行全部 SQL 回归；不为注释或排版回写已在云端执行的迁移。生成类型和接口文档也需跟进。

## 需要合并阅读的替换关系

- handle_new_user：P0 初始化由注册协议迁移替换；旧用户仍保留空协议声明，不给普通角色新增修改权。
- community_create_post：词库/标签迁移新增四参数重载并将三参数重载变成兼容转调；调用者不得给两个重载制造默认参数歧义。
- community_publish/community_feed：最终行为在词库/标签迁移；历史 P1 的图片待审流程不代表当前发布方式。
- community_person：最终行为在协议/获赞迁移；获赞依据当前 published 动态的实际点赞，取消/删除/下架后回读更新。
- community_private.check_text：最终使用 normalize_text；维护词库需保持归一化后的长度约束，普通用户不能访问或修改内部规则。
- public.rls_auto_enable：由 Supabase 平台提供的事件触发基础设施，本仓库的加固迁移只撤销 API 调用权限，不重新定义函数体，因此不计入上表。

## 存储和服务端的配合

pet-media 与 community-media 均为私有 bucket。数据库只记录对象路径并通过触发器排队，storage-cleanup 先验证用户、按用户过滤两个队列，再调用 Storage API。实际文件删除成功后才删除队列项；中断可重试。未关联的孤立上传不由这两个触发器自动发现，处理边界见 [KNOWN-ISSUES.md](KNOWN-ISSUES.md)。

AI reserve/finish 仅开放服务端调用，参数 p_user 必须来自已验证身份；service_role 绕过 RLS，Edge 的额外归属过滤不可省略。失败请求占额度，同 ID 重复受理可取缓存；finish 只接受 pending，重复完成不是第二次成功写入。模型调用与数据库不是分布式事务，保存未知时应先核对历史。

sms_deliveries 没有独立 RPC；send-sms 在事件唯一键上插入抢占，再只更新 pending 到 sent/failed。不要为了追求自动恢复而重发结果未知的同一事件，详见源码注释和 [SMS-SETUP.md](SMS-SETUP.md)。

手工按 comment_id 复核或下架的带条件操作见 [MODERATION.md](MODERATION.md)，不要把针对动态的 community_review 错用于评论。
