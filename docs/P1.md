# P1 功能、权限与验收

2026-10-28 用户确认进入 P1，随后明确选择本阶段仅用敏感词自动审核。继续复用 Vue 3 / Supabase，不增加图表库或另一套后端。P2 话题聚合、搜索、百科和交易均不实现。免费 API 调研与最终选择见 [MODERATION.md](MODERATION.md)。

## 已实现的业务

- 宠物详情的体重折线图：近 7 / 30 / 365 天，至少 3 条有效记录才绘图；展开可读原始数值，不用档案体重造点。同一时间多次称重均保留。每次读取最新最多 2000 条并明确提示上限。
- `/community`：推荐、关注、我的收藏、我的动态。推荐使用发布时间加有上限的点赞/评论权重；20 条分页。排序会随互动变化，客户端对重复 ID 去重，并非个性化推荐模型。
- `/community/new`：1–1000 字、最多 9 张 JPG/PNG/WebP，每张 ≤ 5 MiB、最多 3 个标签且每个 ≤ 20 字；可选本人宠物，只复制名称，经页面说明后主动分享。不会公开宠物 ID、档案、健康记录或私有头像。
- `/community/posts/:id`：全文、图片、点赞/取消、私有收藏/取消、500 字评论、一级回复、本人删除、举报。删除父评论会删除其回复；删除动态级联删除评论及互动，图片排入持久清理队列。
- `/community/people/:id`：独立社区昵称、公开动态、关注/取消、关注/粉丝列表；个人中心提供入口。开通前可浏览，互动需要主动设置社区昵称。

所有社区页面都需登录。社区昵称和已发布内容在已登录的社区成员间可见，原 `users`、`pets`、`records` 的 RLS 没有放宽。收藏和举报仅本人可读。

## 数据库与服务端

`20261028134826_p1_community.sql` 建立 P1，`20261028151228_keyword_moderation_tags.sql` 增量调整自动发布及标签。新增的 8 张 public 社区表开启 RLS，敏感词与每日计数在无普通用户访问权的 `community_private` schema。部署与验收状态以最新测试记录为准。

普通客户端只有 SELECT，写入走有限授权的 RPC。写函数固定空 search_path，使用 `auth.uid()`，检查归属和参数；查询 RPC 使用 invoker 权限保留 RLS。`community_review` 仅授予 service_role。客户端不接触管理密钥。实现遵循 [Supabase 函数权限说明](https://supabase.com/docs/guides/database/functions)。

发帖、评论 UUID 保证相同内容重试不重复；点赞、收藏、关注使用明确的 true/false 状态，重复请求不反转。用户行锁与数据库唯一约束处理并发；每日计数原子更新：发帖 20、评论 100、互动变化 300、举报 20、昵称修改 20，按上海自然日。不设置客户端可以覆盖的额度参数。

独立私有 bucket `community-media` 限制类型和大小；上传只允许本人草稿目录，无 UPDATE 权限。作者可读本人图片，其他成员只能给已发布动态中的图片生成短期链接。[私有存储说明](https://supabase.com/docs/guides/storage/buckets/fundamentals)。更新后的 `storage-cleanup` 已部署，同时清理两个 bucket 各自的本人队列。

## 自动检查与举报复审

文字在数据库过滤敏感词，昵称、标签及宠物名称也检查。基础词库已扩为 28 条，统一全角、部分零宽字符、空格及标点；管理员可维护，不能声称覆盖全部违法内容或所有变体。Vue 用普通文本渲染内容，不解析用户 HTML。**用户明确选择不接入第三方 API，没有图片画面或 OCR 语义审核。**

新文字/图文的配文、标签及宠物名称通过词库检查，图片通过文件和归属检查后即为 `published`，不再要求每条图文人工批准。旧 `pending` 不批量公开，作者可主动点击“重新提交自动审核”；已下架的 `rejected` 不能直接重新发布。管理员核实举报后可在受控 SQL Editor 执行（替换为实际已核查的 ID）：

```sql
-- 只有管理员/服务端可执行，不能在浏览器放 service_role key。
select public.community_review('实际动态UUID'::uuid, true, '人工核查通过');
-- 拒绝或下架：
select public.community_review('实际动态UUID'::uuid, false, '向作者说明具体原因');
```

举报查看 `community_reports` 的 open 行；核对关联动态或评论后，动态可通过上述拒绝动作下架并解决对应举报。评论可由管理员在 SQL Editor 中按实际 ID 删除并复核关联举报；删除父评论会删除回复。允许管理员只修改已核实的内容，不给普通用户管理权限。无需为课设另建管理后台，但正式运营需要明确审核责任人和处理时效。

自动发布、旧内容待重审或人工下架会体现在“我的动态”及详情中。已发出的图片签名链接仍可能在最长 5 分钟内有效，下架不等于撤销旧链接。没有无凭据的定时清理；中途断网产生的未关联文件需周期核查。

## 验收和部署方法

本机运行 `npm.cmd run dev`，登录专用测试邮箱后打开宠物详情或 `/community`。用 A 发含标签和图片的动态、B 查看/点赞/评论/收藏/关注，刷新确认持久化，再验证不能读取对方私有收藏和资料。敏感正文或标签应拒绝；旧待审内容由作者重新提交，举报后仍可由管理员复审下架。

联调脚本需要 `.env.test.local`、进程中的服务端 `TEST_ADMIN_KEY` 及 `TEST_ALLOW_P1_TESTS=yes`；默认跳过，不在 CI 或前端注入这些值。不要在生产项目运行。本次脚本还限定现有开发项目域名，迁移到另一测试项目须先审查并更改目标检查。

前端仍用现有 Pages Direct Upload 方式。自动审核版已生成 `artifacts/pages/pet-nest-pages-20261028-232258.zip`（29 个静态文件，SHA256 `b7780d22d267bff5c8aa53dac9aec2040ae98bdbf7a19f560d74cab97e9dccff`），尚未上传，手机站点仍为之前的 P0 前端。后续构建 `npm.cmd run package:pages` 生成新的被 Git 忽略的 ZIP，检查后再发布。迁移先部署、清理函数再部署、前端最后发布；P1 数据库改动兼容旧前端，不要求删除 P0 数据。不能用本机构建成功代替线上验收。
