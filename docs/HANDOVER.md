## 后续注释约定

- 模块开头解释职责、入口和可信边界；复杂函数说明输入/输出、单位、失败状态及对数据库或外部服务的副作用。
- 对重试、并发、异步清理、频控和时间处理，解释原因与必须保持的约束，并标注相关回归入口。
- 注释与实现同步修改；中文业务说明配合原有英文标识即可，不要求把所有变量改为中文或给显然的赋值逐行加注释。
- 前端校验负责交互，真实权限在 Auth、数据库 RLS/RPC 和 Edge 服务端。不能因为界面有检查就移除服务端检查。
- TS/SQL/接口文档中的状态或字段改变时，同时检查调用者、迁移与测试；运行行为变化需要回归，纯注释/说明修改检查格式和链接即可。

## 接手时必须保持的业务约束

- 私有宠物/记录/AI 数据与社区公开资料分开，owner 从已验证身份获取；Service Role Key 只在服务端。
- AI 新受理请求的额度由数据库事务决定；失败占次、同请求 ID 不重复扣次。不要为了重试便利每次生成新 ID。
- 已收到的 AI 回答立即显示，后台历史同步失败不清空已收到的答案。过期的异步请求不能覆盖当前宠物/会话。
- 图片先上传再关联；响应丢失时先核对数据库引用，无法确认时保留文件。已关联文件清理由持久队列处理。
- 点赞/收藏/关注是“设置为目标状态”，重复请求不能反转状态。社区配文/标签通过词库后发布，图片没有语义/OCR 审核；旧 pending 不批量公开。
- 累计获赞只计算当前已发布动态的实际点赞。协议版本是注册声明快照，不能补造旧用户同意或用其替代身份校验。
- 已执行迁移不删除、不重写；数据库业务调整使用新增迁移，先在独立测试环境验证。

## 新开发者的接手步骤

1. 克隆源码并按 README 安装锁定依赖；当前仓库由用户主动设为公开，推送仍需写入权限。真实配置由维护者通过安全渠道交接，不在 Git、工单或聊天复制密钥。
2. 从 `.env.example` 准备公开前端配置；服务端 Secrets、CLI 授权和平台访问权限分别交接。`.tools` 是被忽略的本机工具，不能假设其他开发者已拥有它。
3. 运行 `npm ci`、`npm run check`、`npm run format:check`、`npm run test:preview`。修改数据库时审查全部迁移并运行 `npm run test:database`；没有 Docker时，PGlite 不代表完整本地 Supabase。
4. 按 TESTING.md 使用两个专用账号验证隔离。full-cloud/gap-cloud 等脚本会写入并清理临时数据，需明确开发环境和所需开关，不能在生产库随意执行。模型、邮件、短信可能产生调用或费用，按实际配置单独验收。
5. 先修一个小改动，能说明“页面 → 调用方法 → 表/RPC → 权限 → 对应测试”，再接手较复杂功能。
6. 发布前端与部署后端分别按文档执行。Pages 当前为 Direct Upload，Git push 不会自动更新网站；发布后需要核对线上资源。Supabase 开发项目不能当作未经验证的正式生产环境。

建议交接验收：新开发者能够独立启动、运行检查、解释一个 AI 重试与一个社区发布异常、定位权限约束，并按说明完成一次测试环境的小改动和验证。当前未有真人接手演练，不能将这一步写成已通过。
